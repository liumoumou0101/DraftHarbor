### F-06 产品边界

- 它是单次执行的资料库维护器，不建设通用 Agent、长期记忆、工具注册、多 Agent、向量数据库、后台定时任务或自主循环。
- 模型不接触文件路径和文件系统，只接收程序提供的当前项目资料卡快照，并返回结构化 JSON 建议。
- 第一版只提供：资料库体检、整理建议、预览差异、应用选中补丁。
- 第一版允许建议修改 `summary`、`tags`、`aliases`、`characterProfile`；禁止修改 `id`、`projectId`、`type`、`category`、`title`、`body`、`sourceReferences`、时间戳和排序字段。
- 第一版不允许删除、合并或创建资料卡；可以报告疑似重复，并给出人工处理建议。
- 小说场景和章节正文不可读、不可写；资料卡 `body` 仅作为分析上下文读取，是否开放修改留到 F-06 完成后的独立决策。
- Agent 使用专门选择的 Provider 配置组；不得隐式继承当前写作模型。API Key 不进入 Prompt、任务历史、日志或补丁数据。
- 所有模型输出都是建议，必须经过 JSON 解析、字段白名单、目标卡存在性、版本一致性和数量上限校验。

##### F-09.6.0 已确认的问题根因

1. 当前从零创作 Definition 是固定的单向链路：`Brief → 方向 → 蓝图 → 资料 → 计划 → 正文 → 审查 → 回流`。审查结束后只会进入回流，回流完成后 Run 结束，没有“下一批”这个运行时动作。
2. `targetLength` 目前只是 Brief 和 Prompt 中的参考值。运行时没有累计正文字数、完成比例、预计剩余批次或达到目标后的停止判断，因此 120,000 字目标不会驱动编排继续运行。
3. 从零创作的正文请求虽然在桌面端按顺序发送，但所有场景 Prompt 在正文阶段开始前一次性准备。第二场及后续场景不会读取前一场刚生成的真实正文和结尾状态。
4. 正文只有全部场景都生成完以后才统一提交并保存。中途关闭应用或后面某场失败时，本轮已经生成但尚未统一提交的正文缺少正式场景级检查点。
5. 共用引导运行内核使用固定的 `plan-result`、`draft-result-N`、`review-result` 产物家族。若直接把节点状态重置到“计划”再次运行，新批次会与旧批次混在同一组产物家族中，无法可靠区分批次、恢复、审查和回流。
6. v2 已经具备区块检查点、滚动状态、不可变 Revision 和应用账本，但从零创作引导界面当前没有接入长篇区块恢复路径；不能简单再写一套并行存储。
7. 当前回流按界面中的正文产物顺序临时生成场景 ID，`applicationId` 也带当前时间。扩展为多批次后必须改成基于批次和场景的稳定身份，否则重复点击或恢复时可能重复创建场景。
8. 工作流没有独立、可版本化的全局写作指令；用户对某一步提出的自然语言修改意见也没有正式产物和作用范围，导致质量调整只能依赖重跑或手工编辑 JSON。

##### F-09.6.1 本轮范围与不做事项

- 第一条落地路径只改“从零创作”引导工作流；契约设计保持可供续写工作流复用，但不在同一阶段同时改造续写和大段重写。
- 持续生成必须由用户逐批确认。每批结束后由用户选择继续、调整后继续、修复本批或结束回流；不建设后台无人确认的无限循环。
- 保留现有 v2 Run、Artifact、Revision、事件、区块检查点和应用账本，不建立第二套正文或工作流 Store。
- 不把环形边加入 Definition。Definition 继续保持可验证的 DAG；“继续下一批”是受控的运行时批次转换，并通过批次产物和事件留下完整轨迹。
- 本轮不启动 F-11 文风档案工程，不做整体 UI 重构，也不把模型能力问题伪装成流程修复。
- 旧运行不得原地迁移。没有批次元数据的既有从零创作运行按“历史单批次运行”兼容，不改写原有磁盘格式，仍可查看、回流和恢复原有路径。

##### F-09.6.2 确定的数据与编排方案

- 新增版本化的 `generation-batch@1` 批次清单产物。每批至少记录：稳定 `batchId`、顺序、目标范围、计划 Revision、正文 Revision 列表、审查 Revision、批次字符数、累计字符数、状态和创建/完成时间。
- 继续复用 `rolling-state@1`，不新增权威正文副本。批次内每场完成后保存已完成场景、上一场结尾摘录、计划结果/钩子和参与人物；批次审查同时产出跨批次使用的剧情摘要、人物状态、未解线索、已知事实和最近结尾。
- 计划、正文和审查产物改用稳定批次身份，例如 `plan-b0002`、`draft-b0002-s0003`、`review-b0002`。批次和场景信息写入现有 Artifact `targetRef`；批准 Revision 仍然不可变。
- 共用引导运行内核增加“由模板决定产物 ID/targetRef”和“只读取当前批次产物”的扩展点，续写、重写和旧运行保持原行为。
- 审查完成后仍进入现有末端决策区，但不自动结束 Run。新增显式“开始下一批”产品 API，把 `plan` 设为 `ready`，把当前批次后的 `draft/review/transfer` 设为 `pending`，保留所有旧批次产物和 Revision。
- `targetLength` 统一解释为用户界面中的“目标正文字符数”；进度使用去除首尾空白后的实际正文字符数计算。目标是参考和提醒，不为了精确凑数截断正文。
- 每批默认由 AI 根据剩余篇幅和蓝图阶段建议 3–6 个场景；用户可在批准计划前修改场景数、顺序和单场目标字数。达到目标后默认突出“结束并回流”，但仍允许用户明确继续。
- 审查出现 `major` 问题时不静默进入下一批。默认提供“根据审查修复本批”“带着审查意见调整下一批”和“我已知晓，仍继续”三种显式选择。
- 回流场景 ID、批次应用 ID 和操作 ID 根据 `runId + batchId + sceneId + sourceRevisionId` 稳定生成；重复提交必须命中既有应用账本，不能重复创建正文。

## 统一规则

- AI 结果一律先进入预览态，不得直接覆盖正文或正式资料。
- 所有写入动作必须由用户确认，并复用现有备份与恢复机制。

- Provider 生成默认请求并消费流式响应；首包等待有上限，reasoning、正文、usage 或有效流数据都会重置空闲计时，活跃流默认不受总墙钟时长限制。
- 新功能必须补充自动化测试，并在本表“完成标准”逐项记录验证结果。
- 功能完成后在此表追加完成日期、测试命令和后续可选优化；若暂停，写明恢复条件。
