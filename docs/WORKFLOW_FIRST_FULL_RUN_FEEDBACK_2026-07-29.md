# 半自动工作流首次完整跑通反馈（2026-07-29）

## 1. 本次里程碑

半自动“从零创作”工作流首次在真实桌面界面、真实项目数据和真实 DeepSeek Provider 下完整跑通。

- 项目：`红斗篷的挽歌`
- Project ID：`project-1785255712769-mjcqyd`
- Run ID：`creation-run-75758728-04ba-4712-a572-f5cbaf78f82f`
- 最终状态：`completed`
- 完成链路：Brief → 创意方向 → 故事蓝图 → 人物与世界观 → 场景计划 → 分场正文 → 自动审查 → 正文回流
- 生成并回流：4 个场景，共约 12,500 个中文字符
- Brief 目标长度：120,000

这证明现有状态机、真实 Provider、产物 Revision、自动审查和正文回流已经形成可工作的首个闭环。以下问题作为后续迭代基线记录；当前优先继续验证功能，不立即进行大规模 UI 重做。

## 2. 本次真实运行证据

### 2.1 等待时间

排除用户阅读和确认时间后，主要生成阶段大致耗时：

- 创意方向：约 38 秒。
- 人物与世界观：约 3 分 38 秒，拆为人物与世界观两个批次。
- 场景计划：约 1 分 42 秒。
- 4 个场景正文：约 4 分 22 秒。
- 自动审查：约 1 分 04 秒。

长等待无法完全消除，但目前除模型思考气泡外，校验、自动修复、产物写入、索引更新、回流准备等阶段缺少连续反馈，容易让用户误判为卡死。

### 2.2 规模限制

本次 Brief 目标为 120,000，但工作流只规划并生成了首批 4 个场景，共约 12,500 字符。当前 `plan` Prompt 明确要求“设计首批可生成的场景计划”，而状态机在一轮 `plan → draft → review → transfer` 后直接结束。

因此“只能生成一个开头”是当前编排设计的确定结果，不是模型偶发少写。工作流尚缺少：

- 当前字数、目标字数和完成比例。
- “继续规划下一批”循环。
- 下一批章节/场景的范围与数量选择。
- 批次之间的滚动摘要、人物状态和未解线索。
- 达到目标、用户主动结束或审查阻断之前持续生成的终止条件。

## 3. 正文质量检查

### 3.1 已经做得较好的部分

- 主题锚定稳定：活体红斗篷、狼灵契约、森林迷宫、代际诅咒贯穿四个场景。
- 场景目标清楚：火场逃生、森林引导、日记揭密、猎人追踪都有明确冲突和结尾钩子。
- 感官描写和黑童话气氛较强，具备可阅读性，不是机械扩写提纲。
- 小红帽与猎人的 POV 能被区分，猎人场景的行动逻辑和修会背景基本成立。
- 自动审查能指出真正的结构问题，而不是只给泛化评价。

### 3.2 明显问题

- 产物仍只是开篇段落，核心交易、迷宫心脏、最终选择和结局方向尚未展开。
- 自动审查确认一个 `major` 问题：蓝图要求的“小红帽主动与狼达成交易”在四个场景中完全缺失。
- 小红帽目前主要被猎人、斗篷、森林和外婆引导，主动选择不足。
- 黑暗意象、身体恐怖和“像……”类比密度偏高，段落几乎持续维持高修辞强度，缺少平静段落和节奏留白。
- 两个 POV 虽然事实和行动不同，但都使用浓密、精雕的暗黑抒情语体，人物语言个性仍不够分离。
- 对话偏少，叙述和感官描写占比过高。
- 猎人的母亲创伤一次交代过多，自动审查也认为这削弱了其前期压迫感。
- “血墨秘录”中从背叛震动到舔血、接受兽性转化过快，情绪过渡不足。

### 3.3 工程侧对质量的影响

质量问题不能全部归因于模型：

1. 当前正文 Prompt 注入 Brief、方向、蓝图、资料草稿、完整场景计划和当前场景，因此主题与事实锚定较好。
2. 四个场景的 Prompt 在正文生成前一次性准备。生成第二、第三、第四场时，不会注入前一场刚生成的实际正文、结尾状态或新增细节。
3. 当前项目的 `styleGuardRules` 为空，工作流 `constraints` 也为空。
4. 工作流没有专门的全局写作指令、文风目标、禁用措辞、句式偏好、叙述距离或对话比例设置。
5. 自动审查只在整批正文生成完成后运行，发现问题时不能在下一场生成前即时纠偏。

因此后续应加入滚动正文上下文和批次内检查，而不是只更换模型或继续加大 Prompt。

## 4. 用户反馈清单与建议方案

### 4.1 过程反馈与可掌控性

问题：

- 步骤之间等待较长。
- 思考完成后到产物出现之间缺少铺垫。
- 用户不知道程序是在解析、修复、写入、建立 Revision，还是已经卡住。

建议：

- 增加与思考气泡同层级的“本步进度”面板。
- 显示用户可理解的阶段：准备上下文 → 请求模型 → 接收正文 → 校验格式 → 自动修复 → 保存产物 → 更新运行 → 等待确认。
- 多批次任务显示 `2/4`、当前场景名、已完成字数和耗时。
- 文件写入只显示逻辑产物与 Revision，不暴露本地绝对路径。
- 失败时保留最后完成阶段、停止原因和安全诊断摘要。

优先级：P1。它不缩短真实耗时，但能显著降低“程序卡死”的感受，并提高测试效率。

### 4.2 按钮命名、位置和步骤切换

问题：

- 主操作名称和位置不统一。
- 开发者也需要思考下一步应点击哪个按钮。
- 当前“生成 → 确认进入下一步”需要两次操作。

建议：

- 每个步骤固定一个主操作区和一致的按钮顺序。
- 统一主按钮状态：`开始生成`、`保存修改并继续`、`确认结果并继续`。
- 次要操作统一为：`提出修改意见`、`重新生成`、`返回上一步`、`查看历史版本`、`取消运行`。
- 后续提供“生成成功后自动进入下一步”和“每步都等待确认”两种半自动级别；默认仍保留确认门。

优先级：P2，功能验证阶段暂缓整体重排。

### 4.3 持续生成大量正文

问题：

- 当前运行一轮只生成首批场景，然后结束。
- 与“快速生成大量文字”的产品目标不一致。

建议：

- 将 `plan → draft → review` 改成可重复的批次循环。
- 每轮允许选择场景数、章节数或目标新增字数。
- 显示累计正文、目标字数、完成比例和预计剩余批次。
- 每轮完成后提供：`继续下一批`、`调整方向后继续`、`结束并回流`。
- 下一批基于已批准正文的滚动摘要、人物状态、未解线索和上一批结尾生成。
- 达到目标长度时提示用户结束，但不强制停止。

优先级：P0，这是半自动工作流的核心产品能力。

### 4.4 生成质量

问题：

- 工程结构能锚定主题，但文风、节奏、人物主动性和跨场承接仍需提高。

建议：

- 不把质量问题简单归因于模型。
- 每生成一场后更新滚动状态，再生成下一场。
- 审查从“整批结束后一次”调整为轻量场间检查 + 批次结束综合审查。
- 增加修辞密度、对话比例、叙述距离、节奏留白、人物声音差异等可选质量规则。
- 审查发现 `major` 问题时，不应让运行无提示地结束；应提供“根据审查意见继续下一批/修复当前批次”。

优先级：P1。

### 4.5 全局写作上下文

问题：

- 缺少专门承载文风限制、全局写作要求、禁用词句、措辞偏好和其他全程约束的位置。

建议：

- 在工作流启动时增加“全局写作指令”，并冻结进运行快照。
- 字段建议：
  - 文风与参考方向。
  - 叙述视角、时态和叙述距离。
  - 句式、修辞密度、对话比例。
  - 必须遵守的表达要求。
  - 禁用措辞、禁用套路和内容边界。
  - 全局补充指令。
- 明确显示该指令会作用于蓝图、计划、正文还是仅正文。
- 允许在批次之间修改；修改后形成新版本，并标明从哪一批开始生效。

优先级：P0/P1。

### 4.6 生成过程中的用户修改意见

问题：

- 用户目前主要只能直接改最终产物或整步重生成，缺少自然语言反馈入口。

建议：

- 每个待确认步骤增加“修改意见”输入框。
- 支持：
  - 按意见重写全部结果。
  - 选择字段、人物卡、场景或正文片段后局部重写。
  - 将意见设为“仅本次”或“加入后续全局指令”。
- 重写生成新 Revision，不覆盖原产物。
- 复用现有 Brief 多字段 AI 重写交互和 Revision 能力。

优先级：P0/P1。

### 4.7 返回、前进、保留与替换

当前事实：

- 已存在“返回到上一步”和“重新生成本步”。
- 返回后，目标步骤变为 `ready`，下游步骤变为 `pending`。
- 历史 Artifact/Revision 不删除，但目标步骤及下游旧产物会被标为过期。
- 重生成会写入同一产物族的新 Revision，旧 Revision 仍保留。

当前不足：

- 没有直接“前进到下一步并复用旧方案”的能力。
- 回退后的旧产物虽然保留，但 UI 缺少清楚的版本选择、比较和恢复入口。
- 用户难以理解“过期”“保留”“替换”的关系。

建议：

- 增加步骤历史和 Revision 选择器。
- 支持比较旧版与新版，并明确选择哪一版作为当前有效方案。
- 回退时让用户选择：
  - 从此步重新生成并使下游过期。
  - 仅查看/修改此步，不立即使下游失效。
  - 恢复一个历史 Revision 作为当前版本。
- 只有上游内容实际改变时，才要求重新生成受影响的下游。

优先级：P1。

### 4.8 结构化结果与原始 JSON

问题：

- 部分步骤只展示摘要。
- 查看全部内容时往往只能进入原始 JSON。

建议：

- 每个结构化产物提供三种视图：
  - 阅读视图：处理后的完整中文内容。
  - 表单/卡片视图：可编辑字段、人物卡、场景卡。
  - JSON 视图：高级编辑和诊断。
- 默认打开阅读或表单视图，JSON 只作为高级选项。
- 摘要不再固定截断为少数项目；允许展开全部。

优先级：P1。

### 4.9 UI 整体问题

现阶段继续以功能闭环、数据正确性、恢复能力和长篇持续生成优先。整体视觉、按钮精修、响应式布局和可访问性专项放到核心工作流稳定之后处理。

优先级：P2。

## 5. 建议开发顺序

1. P0：将单轮开篇工作流扩展为可持续的 `计划 → 正文 → 审查 → 继续` 循环。
2. P0：加入全局写作指令和每步用户修改意见。
3. P1：正文改为带滚动上下文的顺序生成，并加入场间状态更新。
4. P1：增加本步进度/写入进度展示。
5. P1：完善回退、历史 Revision、比较、恢复和替换。
6. P1：为蓝图、资料卡、场景计划和审查提供完整阅读/表单视图。
7. P2：统一按钮、减少不必要的两步切换并整体重做 UI。

## 6. 后续验收标准

- 一个运行能够在用户不新建工作流的情况下连续生成多个批次，直至达到目标或用户停止。
- 第二场及之后的正文明确使用前文滚动状态，不再彼此独立生成。
- 全局写作指令可以验证已进入实际 Prompt，并有版本与生效批次。
- 每一步都可提交自然语言修改意见，并产生可追踪的新 Revision。
- 用户可以返回、比较、恢复和替换历史方案，不丢失旧信息。
- 长等待期间始终能看到当前阶段、批次、耗时和最近完成动作。
- 普通用户无需查看 JSON，也能阅读和修改完整结果。
